Scheduling evolves from individual Pods to groups

Scheduler basicsWhy scheduling is changingWorkload-aware Scheduling

kube-scheduler decides which node runs each Pod

Filter narrows the options. Score picks the best node

1Filter: exclude unsuitable nodes
2Score: rank the remaining nodes
3Bind: assign the best node

The scheduler repeats this for one Pod at a time

This works for web services, where each Pod can start doing useful work on its own

Distributed training needs every worker to be ready

Three workers start, but wait for the fourth. Three GPUs sit idle

Competing Jobs can leave both unable to start

Both A and B stall at 3 / 4. Scheduling one Pod at a time misses the group

So far, projects have built their own solutions outside the core

A shared foundation is taking shape in KubernetesWorkload-aware Scheduling lets the scheduler understand groups of Pods

PodGroup groups Pods. Workload defines the template

Schedule the group only when every Pod fitsGang Scheduling

No partial allocation means no idle workers or deadlock

One scheduling cycle finds a place for the whole group

1Tentatively place all Pods
2Check that every Pod fits
3Bind the group
If the group cannot fit, undo every tentative placement and requeue it

Pods that communicate heavily benefit from staying closeTopology-Aware Scheduling

Scattered Pods pay the cost of cross-rack communication
Keeping workers in the same rack speeds up communication and training

The same selection process now evaluates sets of nodes

1Build candidate placements
2Filter: exclude placements that fail
3Score: pick the best placement
Rack 3 keeps its large block of free capacity for the next big workload

Per-Pod preemption can disrupt part of a workload

The three remaining workers cannot continue training. Three GPUs sit idle

Preemption also needs to consider the groupWorkload-Aware Preemption

A few lines in a Job enable all three features

kind: Job spec: parallelism: 4 scheduling: schedulingPolicy: gang: {} schedulingConstraints: topology: - key: topology.kubernetes.io/rack disruptionMode: all: {} template: ...
Start when all workers are readyGang Scheduling
Keep the group in one rackTopology-Aware Scheduling
Preempt the entire groupWorkload-Aware Preemption

Real workloads often contain nested groupsCompositePodGroup

Example: LeaderWorkerSet with 3 groups, each with 1 leader (L) and 2 workers (W)
Each group forms a PodGroup
A CompositePodGroup groups them together, with up to 4 levels

Each level can define its own scheduling policyCompositePodGroup

Parent policy: all 3 groups in the same zone
Child policy: each group in the same rack
Gang policies work at each level too. Start with 2 of 3 groups: minGroupCount: 2
